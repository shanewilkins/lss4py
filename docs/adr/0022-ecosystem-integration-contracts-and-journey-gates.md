## Context

Individually correct process models, calculations and renderers can produce a
misleading combined artifact if identity, units, cohort or modeled/observed meaning
changes during translation. The first integration must protect the complete
practitioner journey without coupling early-stage package internals.

## Accepted decisions

Numbers preserve the maintainer's decision-review responses.

| # | Decision | Accepted approach |
|---|---|---|
| 1 | First complete journey | A baseline study combining a declared process with realistic observations, parallel work, rework, waiting and incomplete data. Extend the same scenario to before/after verification after its analytical contract exists. |
| 2 | Integration ownership | One optional bridge module initially maintained alongside LSS4PY. Extract a package when demonstrated reuse or independent release needs justify it. Neither package's core depends on the other. |
| 3 | Exchange contracts | Narrow, versioned process projections, analytical evidence and rendering annotations; reuse suitable existing public contracts and keep internal models private. |
| 4 | Identity | Preserve source identifiers and explicit mappings tied to source and model revision. Names are display labels; row position is not identity. Reject ambiguous mappings and unknown step references. |
| 5 | Units, time and order | Declare units, timezone policy and ordering; record explicit normalization/conversion. Ambiguity is an actionable error. Order-dependent methods require an explicit order contract. |
| 6 | Modeled, measured and proposed values | Preserve distinct values and provenance. Begin with separate views or clearly labeled annotations; add overlays only where supported. Never replace modeled values with measurements or invent missing values. |
| 7 | Selection and validation | Adapters validate source structure; LSS4PY owns declared cohort selection and analytical policies; the bridge validates semantic translation; renderers validate presentation inputs. Record changes, exclusions and rejection reasons. |
| 8 | Evidence persistence | A small versioned evidence manifest stores model revision, source references/fingerprints, cohort, methods, parameters, exclusions, units and software versions. Input snapshots are allowed when portability requires them. Real round-trip behavior is required; the existing bundle skeleton is insufficient. |
| 9 | Numerical reuse | Start with NumPy, SciPy and statsmodels. Assess additional dependencies when a concrete need arises; record estimator equivalence and intentional differences. Transparent small domain formulas may remain local. |
| 12 | SixSigma compatibility | Match retained practitioner outcomes and numerical behavior where estimators/domains match; document differences. Calculation and artifact coverage are separate claims. |
| 13 | Version support | Start with the current released packages together. Add version flexibility/matrix breadth when demonstrated needs justify it. Identify exact tested versions and reject unsupported exchange schemas. |

Fast contract checks run on relevant changes; the complete journey is an integration/release gate with explicit maintenance ownership. |

## Open decisions

**10: Statistical plotting refinement.** Matplotlib as the underlying object/export
contract remains the agreed direction. The maintainer favors Seaborn as a convenient
layer and requests further comparison with Matplotlib and ggplot-style Python
options. The exact public plotting API, Seaborn role and defaults remain open.
Regardless of the choice, plotting must preserve already computed evidence and
must not estimate intervals, fit models or change observation order silently.

**11: Fishbone renderer ownership.** Remains open. A future extraction of FLO's
rendering platform into a general rendering package is a possible direction, not
an authorized restructuring or a prerequisite for this integration. Do not assume
fishbones belong in FLO's process model or introduce a general renderer now.

## Responsibilities and enforcement

FLO owns declared process structure, modeled behavior and process diagrams.
LSS4PY owns observed-data analysis, uncertainty, diagnostics and reproducible
results. The workflow/delivery layer composes their public operations. Optional
bridge code translates supported public contracts only; translation does not
re-estimate metrics or convert observations into modeled assumptions.

Existing package import rules remain in force. Integration adds explicit rules
against core cross-package dependencies and bridge imports of private upstream
modules. Version/schema validation happens at exchange boundaries. Unsupported
semantics must be rejected or reported explicitly rather than flattened away.

## Two required test investments

### 1. Cross-package contract suite

Use independent fixtures to exercise process projection and evidence-to-annotation
translation. Preserve identifiers, graph semantics, units, cohort, observation
order, exclusions and provenance. Cover renamed labels, reordered observations,
ambiguous/unknown identities, parallelism, rework, missing metrics and unsupported
schemas/annotations. Render persisted evidence with analytical execution disabled
to prove presentation does not recalculate results.

### 2. Installed-package reference journey

Install the declared current releases outside their source trees. Starting with
a declared process and realistic observations, validate and select an explicit
analysis, persist/reload its evidence, and produce supported process and statistical
artifacts. Verify independent numerical answers, exact step associations, modeled/
observed labels, units, warnings and legible exports. Include a failure variant
that cannot emit an apparently successful study from invalid evidence.

The existing LSS4PY wheel suite ends at analytical JSON export. It is a foundation,
not evidence of a completed FLO integration or diagram/plot journey. Initial work
can establish contracts and fixtures while the plotting refinement is discussed;
dependent rendering implementation waits for that choice.

## Alternatives considered

- Direct internal-object exchange is convenient but exposes unstable internals.
- A universal ecosystem model imposes broad responsibilities before concrete needs.
- Consumer-specific bridges duplicate identity and semantic mapping policies.
- Exact image comparison alone cannot prove analytical meaning and is sensitive
  to platform/font differences; file-existence checks alone miss incorrect output.

## Consequences

This record captures accepted direction and test acceptance targets. It does not
declare an integration implemented, choose a fishbone renderer, extract FLO
rendering, select new numerical dependencies or promote a compatibility claim.
Release identifiers, exchange field definitions and gate ownership must be made
concrete during implementation against supported public interfaces.
