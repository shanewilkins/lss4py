# Installed-package end-to-end tests

From the repository root, run:

```sh
uv run --locked python tools/check_wheel.py
```

To also test published FLO 0.4.2, evidence restoration and Matplotlib/Seaborn
artifact rendering, run `uv run --locked python tools/check_wheel.py --ecosystem`.
Add `--artifacts-dir /tmp/lss4py-ecosystem-artifacts` to retain the source snapshots,
manifest, observed annotation JSON, modeled value-stream SVG and observed SVG/PNG
chart. See the [integration guide](../docs/ecosystem-integration.md).

Pass `--wheel /absolute/path/to/lss4py-0.2.0-py3-none-any.whl` to test an existing
artifact without rebuilding it. The release workflow uses the exact wheel in
`dist/` that it later publishes. With `--artifacts-dir`, the runner also saves
`wheel.json` (filename and SHA-256) and separate `tests/base.xml`, `pandas.xml`,
`storage.xml` and `ecosystem.xml` JUnit reports for the enabled installation
stages, including reports produced by failed test runs. A wheel changed during
verification is rejected.

By default the runner builds the current checkout, creates a fresh temporary virtual
environment, installs the wheel and pytest, and copies this suite outside the
checkout. Python runs in isolated mode; the suite rejects editable/source imports
and leaked development plugins. It then installs the
wheel's pandas extra and repeats the studies on both backends. Dependency versions
are constrained by `uv.lock`. CI runs this same command through Python 3.14.
Pandas currently also arrives transitively through statsmodels in the base install;
the first pass requests no optional extra and exercises Polars. The second pass
explicitly requests the pandas extra and exercises both analytical backends.
Failures in building, installing, the CLI, or any study fail the job. No expected
failures or optional-backend skips are used.

The suite covers:

- Intake CSV → explicit timestamp/stage bindings → lead/wait/PCE and funnel
  yields → descriptive summary → JSON files reopened and checked.
- Unordered event CSV with mapped column names, leading-zero IDs, parallel
  activities and repeated review → topology validation → case lead times in
  hours/minutes → summary and JSON export.
- Inspection CSV with a blank measurement → restored CTQ specification →
  Cp/Cpk, confidence intervals, explicitly shifted Z, grouped summaries and
  missing-data diagnostics → JSON export.
- Corrupt files, missing files/fields/identifiers, invalid timestamps, negative
  durations, undeclared topology, impossible funnel/work durations and strict
  missing-measurement rejection.
- The installed `lss4py doctor` console entry point.

Fixtures are synthetic customer-style data, not customer records. Expected
results are checked in and never generated by lss4py during tests. Intake durations
are hand-subtracted timestamps; wait is elapsed minus active hours; PCE is
100 × value-add / elapsed. The funnel has 4 created, 3 booked, 2 completed items.
Elapsed hours [10, 5, 2, 8] have mean 6.25, median 6.5 and sample std 3.5.
Event cases use earliest start/latest completion, giving 3 and 4 hours regardless
of overlapping work or repeated steps.

The inspection's retained values [8, 9, 10, 11, 12] have mean 10, sample variance
2.5 and limits [4, 16]. Cp = Cpk = 12 / (6 × sqrt(2.5)); shifted Z = 3 × Cpk − 1.5.
The frozen 95% intervals and shifted Z were independently obtained with installed
R 4.6.1 / SixSigma 0.11.1 using:

```r
x <- c(8, 9, 10, 11, 12)
SixSigma::ss.ca.cp(x, LSL = 4, USL = 16, ci = TRUE)
SixSigma::ss.ca.cpk(x, LSL = 4, USL = 16, ci = TRUE)
SixSigma::ss.ca.z(x, LSL = 4, USL = 16, LT = TRUE)
```

Normal test runs require no R installation. Reporting bundles and branch-aware
event-log wait/PCE remain outside these implemented workflows. JSON export uses
the public results' `to_json()` followed by strict JSON disk serialization.

The defect/rework study reads original synthetic `fixtures/defects.csv` counts,
checks opportunity Yield/FTY/RTY/DPMO and optional DPU, exports strict JSON with
explicit denominators, and rejects excess loss. It runs in base and pandas modes.

The data-quality journey reads original synthetic `fixtures/quality.csv`, inspects
missing durations and repeated keys, explicitly selects complete first-key rows,
checks timestamp normalization, calls describe, and exports preparation/analysis
evidence as strict JSON in base and pandas modes.

The audited-bundle journey captures summary/capability results from the checked-in
measurement CSV, links input hashes and specifications, validates the saved JSON
using the packaged standard-library script with site-packages disabled, restores
typed results and explicitly reruns capability after verifying source bytes.
